How does a distributed platform combine real-time events, batch learning, and workload-aware storage while keeping serving latency low?

An event-driven e-commerce platform (Kafka, Spark, HBase, Cassandra, Elasticsearch) built to actually answer that question, not just implement the stack — a workload-aware database optimizer measured on and off, a real-data ALS collaborative filter evaluated at production-realistic sparsity, and fault-tolerance and throughput experiments run against the live system, not simulated.

Research question

The project's architecture exists to answer this — backed by a reproducible experiment under experiments/, not just a design decision. Two further real findings, on a real dataset in each case, are reported alongside it below.

RQ1

Can workload-aware database optimization reduce serving latency without excessive write/indexing overhead?

The autonomous Postgres indexer cut p95 read latency 45% (6.1ms → 3.4ms) for negligible measured write overhead.

FINDING

What does implicit-feedback ALS collaborative filtering look like on real, sparse clickstream data, rather than a curated benchmark?

Precision@10 = 0.0055 on RetailRocket's ~2.75M real events — low mainly because the dataset itself is sparse (median 1 interaction/user), not a bug.

FINDING

Does the real-time item-item recommender's naive similarity lookup actually scale as the catalog grows?

No — live p95 latency grew 8ms to 90ms from 300 to 5,000 items. A precomputed neighbor cache holds it at 0.002–0.054ms throughout.

Architecture

Lambda-style: every event flows through one Kafka topic, consumed independently by a real-time (speed) path and a batch (Spark/HBase) path, with no shared database between services.

Speed layer (top): four independent Kafka consumers, at-least-once, no shared offsets. Batch layer (bottom): HDFS → MapReduce popularity job + Spark MLlib ALS → HBase, served directly as precomputed recommendations (top arrow) -- raw RetailRocket ids, never enriched, since that dataset's ids are disjoint from the demo catalog product-service enriches for the live CF path below it.

Key findings

  • The optimizer earns its keep, at a measured cost. The Postgres auto-indexer cut p95 read latency 45% for negligible write overhead — confirmed against real controlled traffic, not just documented.
  • Real interaction data is honestly sparse. ALS trained and evaluated on RetailRocket's real clickstream events lands at Precision@10 0.0055 — low mainly because the dataset itself is sparse (median 1 interaction/user), not a bug.
  • Elasticsearch genuinely loses its index on container replacement — confirmed via a real container swap, not just a process kill — and only recovers once product-service, not Elasticsearch itself, restarts.
  • The naive CF lookup doesn't scale, and now it doesn't have to. A precomputed neighbor cache turned live p95 latency from 90ms to 0.054ms at 5,000 items — a 1,600–5,100x speedup depending on catalog size.
  • Kafka throughput saturates well below its own unpaced ceiling once a full downstream consumer pipeline is attached — reproduced across two independent runs three weeks apart.
